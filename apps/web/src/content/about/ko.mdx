JulEditor의 이름은 "한 줄, 두 줄" 할 때의 **줄**에서 왔습니다. 글은 한 줄씩 쌓여 문서가 됩니다. 이렇게 쌓인 내용을 편집하고 데이터로 저장한 뒤, 편집 화면을 다시 만들지 않고 읽기 화면에 표시할 수 있도록 문서에 형태를 부여합니다.

## 세 가지 편집 엔진과 JulEditor

자체 편집 엔진을 가진 널리 쓰이는 프로젝트 **Quill, Lexical, ProseMirror**를 비교했습니다. Tiptap도 중요한 에디터지만 ProseMirror를 바탕으로 만들어졌으므로 두 제품을 별도 엔진으로 세면 같은 기반을 중복 비교하게 됩니다. Tiptap에도 [Static Renderer](https://tiptap.dev/docs/editor/api/utilities/static-renderer)가 있어 편집 인스턴스 없는 보기 기능이 JulEditor에만 있는 것은 아닙니다. [Tiptap 구조](https://tiptap.dev/docs/editor/core-concepts/extensions)

| 엔진 | 저장 문서 | 확장과 UI 구성 | 저장 문서 보기 |
| --- | --- | --- | --- |
| **Quill** | [Delta](https://quilljs.com/docs/delta) JSON. `insert`의 흐름으로 문서를 표현하고 서식은 속성에 담습니다. 변경은 `retain`·`delete`도 사용합니다. | 툴바 모듈과 테마로 흔한 UI를 시작할 수 있습니다. 모듈·Parchment Blot·Attributor로 기능과 내용을 확장합니다. [맞춤 설정](https://quilljs.com/docs/customization) | 편집을 끄거나 의미 있는 HTML을 내보낼 수 있습니다. [API](https://quilljs.com/docs/api) |
| **Lexical** | `toJSON()`으로 내보내는 [노드 트리](https://lexical.dev/docs/concepts/editor-state). 실행 중 선택 영역과 노드 키는 저장 JSON과 구분됩니다. | 노드·명령·변환·리스너·[Extensions](https://lexical.dev/docs/extensions/intro)로 기능을 조합합니다. 화면 배치·툴바·메뉴·저장은 앱에서 구성합니다. [소개](https://lexical.dev/docs/intro) | [읽기 모드](https://lexical.dev/docs/concepts/read-only)로 편집을 끄거나 HTML·앱 컴포넌트로 표시할 수 있습니다. |
| **ProseMirror** | 스키마에 맞춘 노드·마크 트리를 `toJSON()`으로 저장합니다. [가이드](https://prosemirror.net/docs/guide/) | 스키마·트랜잭션·플러그인·명령·NodeView로 깊게 제어합니다. UI의 많은 부분은 앱이 구성합니다. [가이드](https://prosemirror.net/docs/guide/) | 편집 불가 뷰와 정적 DOM을 만드는 `DOMSerializer`가 있습니다. [레퍼런스](https://prosemirror.net/docs/ref/) |
| **JulEditor** | 버전이 있는 `{ blocks: [{ id, type, props, content, children }] }` JSON. 등록된 블록 규칙으로 Markdown·HTML을 왕복 변환합니다. | `defineBlock`·`Editor.Plugin`·조합형 컨트롤·렌더러 키로 블록 정의부터 편집과 보기까지 연결합니다. | `Editor.View`가 같은 `Doc`과 사용자 렌더러 키를 React로 출력하며 편집 인스턴스를 만들지 않습니다. |

Lexical의 높은 자유도는 UI를 처음부터 조립하려는 제품에 장점입니다. 그만큼 툴바·메뉴·저장·사용자 노드의 연결 방법도 앱이 결정합니다. JulEditor는 자주 쓰는 React 컨트롤과 일관된 블록 규칙을 함께 제공해 조합 단계를 줄이려 했습니다. Quill과 ProseMirror도 충분히 확장할 수 있습니다. 이 표는 출발점의 차이를 설명하며 우열을 매기지 않습니다.

## 범위를 밝힌 실측

아래 값은 이 저장소에서 잰 것으로, 각 프로젝트의 공식 벤치마크가 아닙니다. 편집 엔트리를 esbuild 0.28.2의 브라우저 ESM·`minify: true`·`es2022` 조건으로 묶고 gzip 크기를 쟀습니다. JulEditor는 `createEditor`와 `coreRegistry`, Lexical은 `createEditor`와 기본 노드, Quill은 기본 엔트리, ProseMirror는 `model`·`state`·`view`를 가져왔습니다. 포함 기능의 범위가 서로 다르고 React UI·CSS·시각 플러그인은 빠져 있습니다. 같은 기능의 제품 크기가 아니라 **대표 엔트리 비용**으로 읽어 주세요.

저장 형식은 같은 평문 **500문단**을 각 형식에 넣었습니다. Node 24.22.1에서 `JSON.parse` 다음 `JSON.stringify`만 5회 예열·20회 측정하고 중앙값을 냈습니다. 타이핑 지연, DOM 렌더링, Markdown·HTML 전체 변환 속도는 아닙니다. Quill의 평문은 하나의 Delta `insert`로 합쳐질 수 있지만 노드 트리는 구조 정보를 명시적으로 보관합니다. gzip 크기와 원본 JSON 크기도 서로 다른 질문에 답합니다.

| 엔진 (버전) | 편집 엔트리 gzip | 500문단 JSON | JSON 파싱+직렬화 |
| --- | ---: | ---: | ---: |
| JulEditor (워크스페이스) | 70.50 KiB | 82.44 KiB | 0.261 ms |
| Lexical 0.52.0 | 67.54 KiB | 141.69 KiB | 0.401 ms |
| Quill 2.0.3 | 58.57 KiB | 43.48 KiB | 0.051 ms |
| ProseMirror 1.25/1.4/1.42 | 55.41 KiB | 71.31 KiB | 0.187 ms |

## 글자 하나를 입력하면 무슨 일이 일어날까요?

키를 누르면 모든 에디터가 같은 다섯 가지 질문에 답해야 합니다. 입력을 어떻게 알아채는지, 변경을 어떻게 기술하는지, 새 데이터는 무엇인지, 화면은 어떻게 따라가는지, 무엇이 저장되는지입니다. 아래 스윔레인 도식은 키 입력 하나가 엔진마다 어떤 순서로 처리되는지 보여 줍니다. 각 줄을 왼쪽에서 오른쪽으로 읽으세요.

<AboutSwimlane>각 줄을 왼쪽에서 오른쪽으로 읽으세요. JulEditor 줄의 태그는 다른 엔진과 같은 부분과 다른 부분을 알려 줍니다.</AboutSwimlane>

가장 큰 차이는 1단계에 있습니다. Quill은 브라우저가 먼저 편집하게 두고 결과를 읽습니다. ProseMirror도 대체로 브라우저의 편집을 읽되 플러그인이 먼저 개입할 수 있습니다. Lexical은 접힌 커서의 일반 텍스트라면 대체로 브라우저가 글자를 넣게 둔 뒤 DOM 변화로 상태를 맞추고, 그 밖의 경우에는 이벤트를 취소하고 모델을 먼저 바꿉니다. JulEditor는 `beforeinput`의 `insertText`를 취소하고 모델을 먼저 바꾼 다음 DOM을 고치므로, ProseMirror가 직접 처리하는 입력 경로나 Lexical의 일반 텍스트가 아닌 경로에 더 가깝습니다. 단순화한 설명이며, 엔진마다 IME 입력이나 붙여넣기 같은 예외 경로가 있습니다. [ProseMirror 가이드](https://prosemirror.net/docs/guide/) · [Lexical 업데이트](https://lexical.dev/docs/concepts/updates) · [Quill Parchment](https://quilljs.com/docs/guides/cloning-medium-with-parchment)

### 비슷한 점, 가져온 점, 다른 점

JulEditor의 모든 부분이 새로운 것은 아닙니다. 아래 도식은 앞선 엔진과 같은 부분과 다르게 선택한 부분을 나눈 것입니다.

<AboutSummary>실선은 개념만 가져온 아이디어, 점선은 비슷한 동작입니다. 상자는 JulEditor가 다르게 선택한 점입니다.</AboutSummary>

평평한 레코드 맵에는 비용도 있습니다. 커밋마다 맵을 복사하므로 편집 한 번의 비용은 여전히 문서 크기에 따라 늘어나고, 위 실측에서도 Quill의 Delta가 더 작고 처리도 빠릅니다. 이 설계가 얻는 것은 적고 예측 가능한 DOM 작업량, 그리고 저장 `Doc`·Markdown·HTML·읽기 전용 React 화면이 함께 쓰는 하나의 블록 규칙입니다. [문서 모델](/docs/core/document-model) · [형식 변환](/docs/core/formats) · [읽기 전용 보기](/docs/core/read-only-view)

| 입력 이후 JulEditor의 경로 | 실제 작업 |
| --- | --- |
| 저장소 → 저장할 `Doc` | `toDoc`이 저장용 트리를 만들되 레코드 키 캐시로 바뀌지 않은 하위 트리를 재사용합니다. |
| `Doc` → Markdown·HTML | 레지스트리가 블록별 변환 규칙을 호출합니다. 대상 형식이 보존할 수 없는 정보는 보고할 수 있습니다. |
| `Doc` → `Editor.View` | 편집 엔진을 마운트하지 않고 React가 블록과 사용자 렌더러 키를 출력합니다. |

Quill의 Delta를 보면 차이를 이해하기 쉽습니다. 저장 문서는 `insert`의 연속이며 줄바꿈에 줄 서식이 붙을 수 있습니다. 변경은 기존 내용을 `retain`하고 새 내용을 삽입하거나 삭제합니다. [Delta 문서](https://quilljs.com/docs/delta)

```json
{"ops":[{"insert":"Release notes"},{"insert":"\n","attributes":{"header":1}}]}
```

## 앱에서 일관되게 꾸미는 방법

문서 코어는 아이콘 라이브러리나 CSS 테마를 가져오지 않습니다. React 컨트롤은 조합형이어서 앱이 툴바와 메뉴에 어떤 동작을 둘지 고릅니다. `className` 슬롯에 Tailwind 클래스를 전달하거나 안정적인 `data-jul-editor-*` 속성에 일반 CSS를 적용할 수 있습니다. 시각 플러그인에는 최소 기본 스타일을 두고, 차트는 `theme`에 색상 데이터를 직접 받습니다. 같은 블록 키로 편집 렌더러와 `Editor.View` 렌더러를 연결하면 저장 문서를 위한 두 번째 파서 없이 제품의 디자인을 이어갈 수 있습니다. [스타일 가이드](/docs/core/styling-i18n-performance) · [커스텀 블록](/docs/core/custom-blocks)

이 프로젝트는 위 엔진들의 설계상 선택과 한계를 살펴보고 코어를 직접 구현했습니다. Quill·Lexical·ProseMirror·Tiptap을 편집 런타임으로 가져오지 않습니다. 이 비교는 선택과 제약을 기록한 것으로, 특정 프로젝트의 코드를 그대로 옮겼다는 주장이 아닙니다.
